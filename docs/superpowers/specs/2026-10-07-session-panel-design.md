# Session Panel: мод с живой панелью статистики сессии

Дата: 2026-10-07. Статус: дизайн утверждён, реализован и выпущен в 0.3.1.

## 1. Цель

Боковая панель (`Pane`) во вкладке Code приложения Claude Desktop, которая в реальном времени показывает данные текущей сессии. Содержание повторяет панель «Work status» из OpenChamber и дополняется журналом сессии как во flightdeck. Внешний вид плоский, как у Desktop Statusline.

Вне рамок:
- скрытие и перестановка секций (секции только сворачиваются);
- кнопка ручного обновления (данные приходят от движка сами);
- уведомления о лимитах;
- анимации;
- поддержка VS Code и mobile.

## 2. Окружение и ограничения

- Движок десктопа 2.1.288. Мод пишется по `claude-code.d.ts`, который скилл `plugin-authoring` генерирует для запущенного движка.
- Модуль работает в изолированной среде без DOM и без Node; наружу ведёт только интерфейс `$`.
- Все хуки мода только наблюдают. Каждый возвращает результат `next(e)` без изменений и никогда не отклоняет и не переписывает промпты и вызовы инструментов.
- Мод не ходит в сеть, не читает токены, ключи и переменные окружения и ничего не пишет на диск, кроме `$.store`. Исключение: временная запись результатов спайка (раздел 8).
- `git` запускается только командами для чтения, которые не пишут индекс и не вызывают `core.fsmonitor`:
  - `git branch --show-current`, `git rev-parse --short HEAD`, `git rev-parse --show-toplevel`;
  - `git status` и `git diff`: они идут с `--no-optional-locks -c core.fsmonitor=false -c diff.autoRefreshIndex=false` и с `GIT_NO_LAZY_FETCH=1` в окружении вызова, `git diff` ещё с `--no-textconv --no-ext-diff`, а `git diff` против HEAD ещё с `-c diff.relative=false`. Фильтры, которые настроил сам человек (например, Git LFS), git при этих чтениях запускает, как при любом `git status`.
  - `git status` и `git diff` против HEAD идут ещё с `--ignore-submodules=dirty`: git не обходит рабочее дерево
    сабмодуля;
  - `git diff --no-index` для нового файла идёт ещё с `GIT_ATTR_SOURCE=4b825dc642cb6eb9a060e54bf8d69288fbee4904`
    (пустое дерево git) в окружении: `.gitattributes` не действует, и фильтр, выбранный атрибутом, на неотслеживаемом
    файле не запускается;
  - первый `git status` идёт без флага `-u`, и git следует `status.showUntrackedFiles` человека; второй, с `-uall`,
    идёт, только если первый перечислил неотслеживаемую папку (4.1);
  - все вызовы git одного чтения изменений делят один срок в 30 с (4.1);
  - изменения (`git status`, `git diff`) мод читает только с первого хода основного агента, а до него читает папку и
    ветку (4.1).

### 3.1. Визуальные правила (по образцу Desktop Statusline)

- **Шкала** — SVG высотой 8px, обе полосы со скруглением `rx=4`:
  - дорожка `#808080` с `fill-opacity 0.3`;
  - заливка `#2f7de1` ниже 80%, `#e0a030` от 80%, `#e5484d` от 95%.

  Ширина шкалы считается от `bodyColumns` по 8 px на ячейку; формулы и пределы — в визуальной спецификации (`2026-10-07-session-panel-visual.md`, §6.2 и §6.5). На поверхности без `Svg` вместо шкалы выводится текст `▰▱` (10 делений).
- **Цвет текста** — ключи темы:
  - процент шкалы: `warning` от 80%, `error` от 95%;
  - Cache: `success` от 50%;
  - статусы: running — `#2f7de1`, ✓ — `success`, ✗ — `error`;
  - второстепенное — `dimColor`.
- **Заголовок секции** — `Button` (`plain`) с меткой `▾ Usage` (`▸` когда свёрнута) и справа приглушённая сводка.
- **Без сворачивания** только блоки Session и Project.
- **Строки «метка — значение»** раскладываются через `justifyContent: space-between`.

### 3.2. Форматы

| Что | Формат |
|---|---|
| Деньги | ≥ $1: 2 знака (`$5.49`); < $1: 3 знака (`$0.152`), но ветка выбирается после округления, поэтому 0.9995 ≤ x < 1 даёт `$1.00`; < $0.001: `<$0.001` |
| Context % | 1 знак (`12.8%`) |
| Лимиты и Cache | целое (`24%`) |
| Токены | < 1000 как есть; < 10k: 1 знак (`2.3k`); < 1M: целое (`128k`); иначе `1.2M` (`.0` отбрасывается) |
| Длительность | < 60 с: 1 знак (`33.5s`); < 1 ч: `1m 05s`; иначе `1h 02m` |
| TTFT | < 0.1 с: `<0.1s`, иначе как длительность |
| Скорость | `~104 tok/s` (целое) |
| Сброс лимита | `↻ 45m`, `↻ 2h 13m`, `↻ 5d 15h` |
| Время в журнале | локальное `HH:MM:SS` |

## 4. Данные и формулы

Все пути API сверены с d.ts 2.1.288. Номера строк исполнитель уточняет по типам сам.

### 4.1. Session и Project

- **Context:**
  - токены — `context.tokens` из `session.measure` (несёт `context`, `rateLimits`, `cost`, `changed`), `usage()` и после `session.compact`;
  - окно — `breakdown.rawMaxTokens` из `usage({ breakdown: 'summary' })`. Это окно компакции с учётом ручной настройки (`autoCompactWindow` в settings; источник указан в `autocompactSource`). Если разбивки нет, берётся `context.window` (окно модели). Окно обновляется на `session.start` и таймером вместе с MCP. При смене модели (окно в `session.measure` изменилось) разбивка `usage({ breakdown: 'summary' })` перечитывается сразу, не дожидаясь таймера;
  - процент = токены / окно × 100, считается модом: `context.percent` движка считает от окна модели;
  - до первого ответа модели выводится `—`.
- **Total:** `usage().cost.usd`. Если поля нет (у хоста нет учёта стоимости), строка Total скрывается.
- **Subagents:** Σ стоимостей субагентов, измеренных по приросту `cost.usd` (4.4). **Session** = `max(0, Total − Subagents)`. Строка показывается, только если Subagents > 0. Спайк подтвердил, что `cost.usd` включает субагентов.
- **Project:** basename от `$.session.root()`. Поле `repo().name` не использовать: оно null для обычных репозиториев. Это отдельный блок после Session, как в OpenChamber: жирный заголовок `Project` и имя папки справа (решение пользователя от 2026-10-08). Без имени блока нет.
  - из имени убираются символы форматирования Unicode (категория Cf, 4.7): U+202E переставил бы то, что панель
    показывает после него.
- **Branch:**
  - источник: `$.process.run(['git', 'branch', '--show-current'], { cwd: root, timeoutMs: 5000 })`;
  - если ветка пустая (detached HEAD), берётся `git rev-parse --short HEAD`;
  - из названия убираются символы форматирования Unicode (4.7);
  - если это не git-репозиторий, ветка скрывается.
- **Changes:** изменения рабочего дерева относительно HEAD: число файлов и число добавленных и удалённых строк (`+добавлено / −удалено`).
  - файлы: каждая запись `git status --porcelain -z`, кроме игнорируемых. Это изменённые, добавленные в индекс,
    удалённые, конфликтные и каждый новый файл; переименование считается один раз. Неотслеживаемые файлы читаются по
    настройке человека:
    - первый `git status` идёт без флага `-u`, поэтому git следует `status.showUntrackedFiles`: при `no` ни один
      неотслеживаемый файл не обходится (так настраивают репозиторий dotfiles в `$HOME`, чтобы git не обходил домашнюю
      папку), при `normal` неотслеживаемая папка выводится одной записью `dir/`;
    - только если в этом выводе есть неотслеживаемая папка (запись `?? ` с `/` на конце), идёт второй `git status` с
      `-uall`, и берётся его вывод: в нём файлы папки перечислены по одному;
    - остальные флаги (`--porcelain -z --ignore-submodules=dirty`) и бюджет у двух вызовов общие, и оба считаются
      вызовами `git status` для остановки чтения (ниже); второй, который не удался, — сбой `git status`: в этом чтении
      изменений нет;
    - вложенный репозиторий, например worktree внутри репозитория, не попавший в игнор, git всегда выводит как
      неотслеживаемую папку, поэтому с ним каждое чтение запускает оба вызова; это тоже ограничивает бюджет;
  - строки отслеживаемых файлов: `git diff --numstat … HEAD --`, чистая разница с HEAD;
  - строки новых файлов: по одному `git diff --no-index --numstat … -- /dev/null <файл>` на файл, но только для первых `NEW_FILES_MAX` (50) новых файлов; дальше плюс — нижняя оценка. `--no-index` завершается кодом 1, если стороны различаются, и для пустого нового файла тоже, поэтому принимаются коды 0 и 1. Бинарные файлы дают 0;
  - флаги `git status` и обоих `git diff`, каждый со своей причиной:
    - `--no-optional-locks`: обычный `status` может обновить индекс и взять `index.lock`, из-за чего упадут git-команды самого человека или агента;
    - `-c core.fsmonitor=false`: fsmonitor может запустить хук или демон;
    - `-c diff.autoRefreshIndex=false`: если сравнение с рабочим деревом нашло файлы, у которых изменились данные stat, а содержимое нет (`touch`, форматтер, переписавший файл без изменений), `git diff` обновляет индекс: берёт `index.lock` и переписывает `.git/index`, и `--no-optional-locks` этого не останавливает. Воспроизведено на git 2.43: без флага sha индекса менялась, с флагом осталась прежней;
    - цена `--no-optional-locks` и `-c diff.autoRefreshIndex=false`: индекс не обновляется никогда, поэтому каждый
      `git status` (их два, если первый нашёл неотслеживаемую папку) и `git diff` против HEAD при каждом чтении заново
      хешируют файлы, у которых изменились данные stat, и clean-фильтр на изменённом отслеживаемом файле может сработать
      за одно чтение до пяти раз (с git 2.43 — по разу в каждом `git status` и два-три раза в `git diff`); границу дают
      бюджет чтения и задержка между чтениями (ниже);
    - `GIT_NO_LAZY_FETCH=1` в окружении вызова: в частичном клоне `git diff` иначе докачал бы недостающие объекты с
      promisor remote, а это сеть. Переменную учитывает git 2.44 и новее, а также некоторые сборки 2.43 в
      дистрибутивах (бэкпорт); остальной git её игнорирует;
    - `--no-textconv --no-ext-diff` (оба `git diff`): они считают сами файлы и не запускают textconv и внешние программы diff;
    - `-c diff.relative=false` (`git diff` против HEAD): если у человека задано `diff.relative=true`, а корень сессии лежит ниже корня репозитория, числа строк иначе покрыли бы только папку сессии. Параметр `--no-relative` появился только в git 2.28, поэтому вместо него переопределяется настройка; более старый git ключ игнорирует;
    - `--ignore-submodules=dirty` (`git status` и `git diff` против HEAD): git не обходит рабочее дерево сабмодуля;
    - `GIT_ATTR_SOURCE=4b825dc642cb6eb9a060e54bf8d69288fbee4904` (пустое дерево git) в окружении каждого вызова
      `git diff --no-index` для нового файла: ни один `.gitattributes` не действует, поэтому на неотслеживаемом файле
      не запускается фильтр, выбранный атрибутом (clean или process, например Git LFS). `.git/info/attributes` и файл
      атрибутов, который называет `core.attributesFile` (в настройках git человека или в `.git/config` самого
      репозитория), продолжают действовать: ни то, ни другое не приносит ни один клон. Git, который не знает
      `GIT_ATTR_SOURCE`, её игнорирует. Репозиторий SHA-256 отвергает этот идентификатор, поэтому у его новых файлов
      строки не считаются (помечено, если строки есть: `+A+`, ниже; без строк чисел нет);
    - `GIT_CEILING_DIRECTORIES` не задан: мод не читает переменные окружения, поэтому не знает `$HOME`. Потолок на
      `$HOME` лишь не дал бы папке вне git внутри `$HOME` прочитать репозиторий в самом `$HOME` (папку, в которой git
      запущен, он с потолком не сверяет), а потолок, который останавливает поиск на корне сессии (задан на его
      родителе), скрыл бы репозиторий сессии, начатой в одной из папок репозитория. Поэтому сессия в такой папке читает
      этот репозиторий, как и `git status` в ней, в пределах бюджета чтения;
    - фильтры, которые настроил сам человек (clean и process, например Git LFS), при этих чтениях всё равно запускаются, как при любом `git status`. Это принято: это собственная настройка git человека;
  - `git rev-parse --show-toplevel` даёт cwd для диффов новых файлов: пути в `status` отсчитываются от корня
    репозитория, а он может не совпадать с корнем сессии; если `git rev-parse --show-toplevel` не удался (не сделан,
    убит таймаутом или вышел с кодом не 0), новые файлы остаются несчитанными, а строки диффа стоят нижней оценкой
    (`hasMoreAdded`);
  - таймаут каждого вызова — 10 с, но не больше времени, которое осталось от срока чтения (ниже);
  - бюджет чтения:
    - изменения одного чтения читаются за 30 с (`READ_BUDGET_MS`), считая от начала чтения изменений. Каждый вызов git,
      которым они читаются (статусы, `git diff` против HEAD, `git rev-parse --show-toplevel`, подсчёт новых файлов),
      идёт с таймаутом, равным меньшему из 10 с и оставшегося времени. Когда времени не осталось, следующий вызов не
      делается, и чтение кончается так, как кончилось бы при сбое этого вызова: без `git status` изменений нет, без
      `git diff` против HEAD `lines` равно `null`, без `git rev-parse` или подсчёта нового файла цикл по новым файлам
      останавливается с `hasMoreAdded`. Зачем: каждый вызов укладывается в свой таймаут, но вызовы одного чтения
      складываются: 50 новых файлов по 9 с — это минуты;
    - цикл по новым файлам останавливается на первом сбое (таймаут, код выхода, не равный 0 и 1, обрезанный вывод);
      уже посчитанные строки остаются как нижняя оценка;
    - для каждой папки считается, в скольких чтениях подряд `git status` или `git diff` против HEAD бросил исключение
      (таймаут или git, который не удалось запустить; ненулевой код выхода, как вне репозитория, не в счёт). Чтение, в
      котором это было, прибавляет к счёту папки единицу, а чтение, в котором и `git status`, и `git diff` закончились
      без исключения, обнуляет его. Дойдя до двух (`READ_THROWS_MAX`), чтение изменений папки останавливается на 15
      минут (`READ_RETRY_MS`), считая от начала чтения, которое его остановило; ветка по-прежнему читается, а строка
      изменений просто не показывается, без пометки. Первое чтение после этого срока пробует снова: с исключением папка
      ждёт ещё 15 минут, без него счёт обнуляется. Иначе сессия внутри огромного дерева, например репозитория dotfiles в
      `$HOME`, тратила бы весь таймаут на каждое чтение, а без повторной попытки сон компьютера или занятый диск во
      время двух чтений подряд останавливали бы папку навсегда;
    - счёт ведётся по папкам: чтение другой папки его не сбрасывает и срок ожидания остановленной папки не меняет;
  - нижние оценки помечаются плюсом:
    - если вывод `git status` обрезан (предел вывода 4 МиБ, который может превысить неигнорируемый `node_modules`),
      берутся только целые записи, строка читается `N+ files changed` (всегда во множественном числе, и для одного
      файла: `1+ files changed`), а чисел строк нет: диффы не запускаются, `lines` равно `null`;
    - если новые файлы сверх первых 50, файл, у которого счёт не удался, или корень репозитория, который не удалось
      получить, не прибавили строк, у числа добавленных строк стоит плюс: `+2061+ / −4`. Нижняя оценка без строк
      (`+0+ / −0`) чисел не показывает, как и неизвестные строки: так бывает в репозитории SHA-256 с одними новыми
      файлами и когда не удался первый счёт нового файла или не удалось получить корень репозитория;
  - что скрывается: сама строка Changes — вне репозитория, на чистом дереве, при сбое git, до первого хода основного
    агента и для папки, чтения которой остановлены; числа в ней — если число строк неизвестно (нет HEAD, сбой
    `git diff`, обрезанный `status`) или оба счётчика равны 0 (изменились только бинарные файлы): тогда показано одно
    число файлов;
  - файлы мод не читает: строки считает git.
- **Когда обновлять** (ветку и изменения вместе):
  - триггеры: `session.start`, `turn.complete` основного агента, `classic.CwdChanged`, а также вызов Edit, Write, MultiEdit, NotebookEdit или Bash любым агентом, если вызов не отклонён и ядро не выполнило его только на чтение (в результате вызова стоит `isReadOnly`; ядро ставит его, например, для Bash `ls`);
  - первый ход: изменения (`git status`, `git diff`) читаются, начиная с первого хода основного агента: его
    `turn.start` (без `agentId`) открывает чтение изменений и просит одно. До него блок показывает только папку и
    ветку: `git branch` фильтров не запускает, а `git status` и `git diff` могут запустить фильтры, которые назвал
    конфиг самого репозитория, и ход не начнётся, пока человек не принял папку. Перезагрузка мода снова ждёт
    следующего хода. Условие выполняется один раз за сессию, а не для каждой папки: папка, в которую сессия перешла
    позже (`classic.CwdChanged`), читается сразу;
  - задержка перед чтением после такого вызова — большее из 1 с и четырёх длительностей последнего чтения
    (`PROJECT_GAP_FACTOR`, 4). Так git занимает не больше примерно четверти времени для чтений после вызовов
    инструментов даже в большом репозитории (таймер запускается в момент вызова, а он может прийти во время предыдущего
    чтения; четверть верна для чтений не дольше минуты, а более долгое чтение засчитывается за минуту, ниже), а чтение,
    упёршееся в таймауты, не повторяется сразу;
  - раз в минуту, пока панель размещена и показана (`isPlaced` и `isShown`): на каждом втором тике таймера в 30 секунд
    проект читается и сам по себе, с тем же правилом задержки (четыре длительности последнего чтения). Так правки не
    через инструменты Claude (редактор, терминал, фоновая команда, закончившаяся после возврата своего вызова) видны без
    нового хода. «Показана» у движка значит «впереди других плагинных панелей сессии», и панель Session, когда она одна,
    показана всегда, какую бы вкладку или сессию ни вывел вперёд десктоп. Поэтому в обычной настройке минутное чтение
    идёт, как в 0.3.0 (тик смотрел только на `isPlaced`), в каждой сессии с открытой и размещённой панелью, а границу
    ему дают правило задержки и бюджет чтения. Чтение примерно через секунду после правки или команды, которая не только
    читает, остаётся, как и чтения после конца хода основного агента и `classic.CwdChanged`: от панели они не зависят.
    Открытие панели (`/session-panel` или автооткрытие на `session.attach` десктопа) просит чтение сразу, а старт сессии
    читает и так. Зачем: до 0.3.0 простаивающая сессия git не запускала, а закрытой панели, панели, которая ждёт
    размещения, и панели, которую перекрыла другая плагинная панель сессии, некому показывать изменения. Закрывает ли
    это условие находку живой проверки 0.3.0 (п. 2: каждая живая сессия читала дерево раз в минуту), зависит от того,
    снимает ли десктоп размещение панели у сессии, которую не показывает. Живая проверка 0.4.0 нашла, что встроенная
    вкладка Terminal впереди не снимает с одиночной панели ни размещения, ни показа, так что минутное чтение идёт;
    пользователь решил оставить его как есть (2026-10-13; раздел 8, проверка 13);
  - длительность чтения в правиле задержки засчитывается не больше чем в минуту, поэтому ожидание после медленного
    чтения — не больше четырёх минут. Зачем: чтение измеряется по настенным часам, и приостановка машины посреди чтения
    иначе остановила бы минутное чтение на четыре длительности сна;
  - чтения идут по одному: запрос во время чтения помечает проект устаревшим, и сразу после этого чтения идёт ещё одно;
  - вызов, пришедший, пока отложенное чтение ждёт таймера, ничего не добавляет. Ожидание старше удвоенной меньшей из двух задержек — своей и той, какую получило бы новое ожидание, — считается потерянным (хук отклонил таймер), и следующий вызов ставит новый таймер; так ожидание, поставленное после медленного чтения, не переживает быстрое;
  - ветка пишется первой: чтение записывает имя и ветку сразу, а изменения — когда они посчитаны. Если имя папки сменилось, прежние изменения сбрасываются сразу, чтобы число из другой папки не показывалось под новым именем.

### 4.3. Turn stats

Показывается последний **завершённый** ход основного агента: события без `agentId`, между `turn.start` и `turn.complete` с одним `turnId`. Ход, прерванный до первого ответа (ни одного шага), предыдущий не заменяет. Пока идёт новый ход, на экране остаются данные предыдущего.

**Замер шага.** Хук `turn.step` — асинхронный генератор. Внутри него:
- `tStart = await $.clock.now()` при входе;
- `tFirst` — момент первого чанка любого вида, включая служебные `engine`: это начало ответа API. Блок `thinking` приходит одним чанком уже после того, как размышление закончилось (через 6–51 с), поэтому по нему TTFT не считается;
- `tEnd` — момент чанка `stop`, из него же берётся `usage`;
- флаги `hasTool` и `hasText`.

Чанки передаются дальше без изменений. `await` делается не больше трёх раз за шаг.

**Инструменты.** Хук `tool.call` основного агента (без `agentId`) замеряет `t0 = await $.clock.now()` до `await next(e)` и `t1` после, и записывает интервал `[t0, t1]`. Интервал включает ожидание разрешения, если оно было. Спайк показал, что `classic.PostToolUse*` до мода не доходят.

Формулы:

| Метрика | Формула |
|---|---|
| Elapsed | `turn.complete.durationMs` |
| Model time | Σ (`tEnd − tStart`) по шагам |
| Tool time | длина объединения интервалов инструментов (пересечения склеиваются) |
| Steps | число шагов, дошедших до `stop`; строка показывается, только если шагов больше одного (как в OpenChamber) |
| Average TTFT | среднее (`tFirst − tStart`); если хоть у одного шага нет `tFirst`, то `null` и строка скрыта |
| Whole turn | Σ `output_tokens` / Model time |
| Response | у последнего шага, если в нём нет `tool` и есть `text`: `output_tokens` / (`tEnd − tStart`); иначе `null` и строка скрыта. Окно считается от отправки запроса: финальный текст иногда приходит одним пакетом за десятки мс, и окно от первого чанка давало абсурдные значения (~3000 tok/s, живая проверка 2026-10-07) |
| Tokens | `↑` = вход не из кеша (ниже), `↓` = Σ `output_tokens`; источник `turn.complete.usage`, иначе сумма по шагам |
| Cache | Σ `cache_read` / Σ (`input` + `cache_read` + `cache_creation`) |
| Cost | `usage().cost.usd` сразу после `next(e)` в `turn.complete` минус значение на `turn.start`. Включает субагентов, работавших в этом ходе |

`↑` в Tokens — то, что ход отправил по полной цене или дороже: Σ (`input_tokens` + `cache_creation_input_tokens`), то
есть вход, который не был закеширован, и то, что записано в кеш (запись стоит дороже обычного токена). Чтение из кеша
дешёвое и в `↑` не входит: его показывает Cache, и долю Cache это не меняет (Σ `cache_read` / Σ (`input` +
`cache_read` + `cache_creation`)). Зачем: в 0.3.0 `↑` был всем входом хода (`1.1M ↑` за ход), то есть «контекст ×
шаги», и не следовал за стоимостью (решение пользователя от 2026-10-09 по живой проверке 0.3.0). Пример: обычный ход —
`3.1k ↑`, ход после того, как кеш остыл, — `92k ↑`. Теперь `↑` следует за стоимостью лишь приблизительно: чтение из кеша
стоит десятую часть цены входа, но в длинном ходе с большим контекстом может составить большую часть стоимости, а в `↑`
оно не входит.

Скорость, которая выходит за 5000 tok/s или считается по окну ≤ 0, становится `null`. Сводка в заголовке — Response, при его отсутствии Whole turn.

### 4.4. Subagents

**Записи субагентов:**
- `agent.spawn`: после `next(e)` берётся `{ model, agentId }` из результата и описание с типом из входа, плюс время
  старта. Из описания и типа убираются символы форматирования Unicode (4.7): U+202E переставил бы то, что показывает
  список;
- `turn.step` с `agentId`: после чанка `stop` к записи прибавляется стоимость шага (см. «Стоимость» ниже);
- `turn.step` с `agentId`, чья запись уже закрыта: субагента продолжили сообщением (SendMessage). Запись снова `running`, `endedAt` сбрасывается, в журнал пишется `resumed · ${type}: ${description}`. Продолженный субагент сохраняет свой id; `agent.spawn` для него не срабатывает, а у `turn.start` нет `agentId`.
- `turn.complete` с `agentId`: статус и время окончания (`reason`, `isAborted`), а также `answer` для журнала;
- таймер 30 секунд: `$.agent.list()` уточняет статусы (если субагента остановили не нашими событиями).

**Строка списка:** значок статуса; `description`, которое занимает всё оставшееся место; приглушённый `@type` (часть после последнего `:`) в столбце постоянной ширины, поэтому типы начинаются на одной позиции в каждой строке; справа `$`. В узкой панели `@type` уходит первым: если описанию рядом с ним осталось бы меньше 12 ячеек (`MIN_AGENT_DESC_CELLS`), столбца `@type` нет ни в одной строке. Ширины столбцов и правило 12 ячеек — в визуальной спецификации, §6.7.

**Порядок:** сначала работающие, затем по времени старта, новые выше. Не больше 8 строк, остальные сводятся в `+N more`. Сводка в заголовке: `running/total`, если кто-то работает, иначе `total`.

**Стоимость** измеряется по движку, без таблицы цен и без сети. Спайк показал: `cost.usd` растёт сразу после завершения каждого запроса модели, и прирост точно равен цене запроса.
- После каждого чанка `stop` (любого агента) мод через `$.clock.after(1, …)` читает `usage().cost.usd`. Чтения идут строго по очереди. Каждое чтение заодно обновляет Total.
- Прирост `delta = usd − lastUsd` записывается на агента этого шага: основной агент (`main`) или субагент (`agentId`).
- `lastUsd` вначале равен `null`, в том числе после перезагрузки мода, после `/clear` и после `resume`. Первое чтение и чтение ниже `lastUsd` (учёт обнулился) только задают базу, без прироста.
- `turn.complete` субагента сначала дожидается своего чтения, а потом пишет итог в журнал.

Погрешности, которые не влияют на сумму:
- запросы двух агентов, завершившиеся в пределах 1–2 мс, могут перепутаться;
- когда субагенты работают одновременно, атрибуция приблизительна: каждый прирост `cost.usd` уходит агенту, чей шаг
  только что завершился, поэтому перекрывающиеся шаги могут записать на одного агента запрос другого. Один и тот же
  субагент стоил $0.100 рядом с параллельным ревью и $0.046 один (живая проверка 0.2.0, п. 14). Итоги точные:
  Total = Session + Subagents;
- фоновые служебные вызовы движка (классификатор разрешений, компакция) приписываются агенту, чей шаг завершится следующим.

### 4.7. Log

Хранятся последние 200 записей (до 0.4.2 — 60) `{ at, who, text, kind: 'info' | 'ok' | 'error', outcome? }`, новые
сверху. Сколько строк рисует панель, что показывает заголовок и когда внизу появляется строка `+N more`, с 0.4.0
определяет спецификация v2, §3 (`2026-10-12-session-panel-v2-design.md`). Как журнал заполняет высоту, сказано в
разделе 5. Записи порождают:

| Событие | who | text | outcome |
|---|---|---|---|
| `turn.start` | `you` (`engine`, если текст начинается с `<`) | `shorten(redact(text), 70)`; для `engine` — имя тега | — |
| `tool.call` (после `next(e)`) | `main`, тип субагента (до 14 символов; обрезанный кончается на `…`) или `agent` у агента, которого нет среди субагентов (например, форк движка) | `shorten(redact(label), 64)`, где `label` = `${tool} ${target}`. Успешный вызов Agent/Task, успешный SendMessage на id известного субагента и успешный `SubagentHandback` субагента не пишутся: о них говорят строки `spawned`/`resumed` и итог субагента. Неудачные и запрещённые вызовы пишутся. | `✓ 0.3s`; `✗ 0.3s` у неудачного вызова (время есть и у него); `denied` у запрещённого; у агента без строки в Subagents неудачный и запрещённый вызов тусклые (`kind: 'info'`): форк движка, которому ядро отказывает во всех инструментах, иначе давал бы красную строку, которую никто не вызывал (живая проверка 0.4.1) |
| `agent.spawn` | `main` | ``shorten(redact(`spawned · ${type}: ${description}`), 70)`` | — |
| `turn.step` субагента, чья запись закрыта | `main` | ``shorten(redact(`resumed · ${type}: ${description}`), 70)`` | — |
| `turn.complete` с `agentId` | тип субагента | `done · $0.02 — ${answer до 80}`, где `answer` — `e.answer`, а если он пуст или из одних пробелов, то запомненное сообщение `SubagentHandback` (стоимость — только если она известна, ` — ответ` — только если он не пуст) или `failed` (`kind: 'error'`) / `stopped` (`kind: 'info'`, остановка не ошибка; в списке — приглушённый ✗) | `✓ 1m 12s` у `done`, `✗ 1m 12s` у `failed`, `1m 12s` без значка у `stopped` |
| `session.compact` | `main` | `compacted 180k → 40k` | — |

Перед `redact` (а у ответа субагента — перед `plainText`) каждый текст журнала очищается от символов форматирования
(`stripFormat`) и обрезается до первых 4096 единиц UTF-16 по пробелу (`wordHead`, `TEXT_HEAD_MAX`): слово, которое
разрезала обрезка, отбрасывается, чтобы секрет не оказался разрезан надвое. Зачем: шаблон URL в `redact` и шаблон пар в
`plainText` на длинном подобранном тексте работают квадратичное время, а панель показывает не больше 80 символов.
Отбрасывается только слово не длиннее 256 единиц (`CUT_WORD_MAX`): более длинное слово (длинный URL, base64, minified
JSON, абзац CJK без пробелов) и текст без пробелов в первых 4096 единицах режутся по символам, и панель показывает их
начало (решение пользователя от 2026-10-14 по живой проверке 0.4.1). Шаблоны, которые узнают секрет по имени
(`password=`, `Bearer`, `sk-`), маскируют длинное значение и с его начала; маску может потерять пароль в URL, который
разрезала обрезка, если отрезок без пробелов вокруг разреза длиннее 256 единиц (длинный пароль или пароль, приклеенный к
другим видимым символам); увидеть его можно лишь в подобранном тексте, и это принято как best effort. Невидимые символы
(Cf) убираются ещё до обрезки, поэтому прокладкой они не служат.

**Отчёт субагента в авто-режиме.** Субагент отчитывается вызовом инструмента `SubagentHandback` со входом `{ message }`. Такая форма видна в транскриптах (47 из 47), в типах движка её нет, поэтому берётся только `message` типа `string`. В `turn.complete` такого субагента `answer` пуст. Успешный вызов в журнал не пишется, а `message` запоминается за агентом; неудачный или запрещённый вызов пишется, как любой другой. Строка `done` берёт запомненный текст, если `answer` пуст или из одних пробелов; текст проходит `redact` и `shorten`, как любой ответ. Текст служит один раз: `turn.complete` агента снимает его при любом исходе, а `/clear` и `resume` сбрасывают непрочитанные. Если авто-режим не передал отчёт родителю (в результате вызова `Agent` у родителя `handback: 'withheld'`), строка `done` его всё равно показывает: вызов самого субагента удался.

**Задержанный или помеченный отчёт.** Строка `done` показывает отчёт и когда авто-режим его пометил
(`handback: 'flagged'`), и когда задержал (`'withheld'`, выше): живая проверка 0.2.0, п. 10. Текст замаскирован, а
главный агент его не получил. Это не менялось и остаётся известным ограничением.

Исход (`outcome`) необязателен: у строк без действия (промпт, `spawned`, `resumed`, сжатие) его нет. Панель рисует его
столбцом у правого края строки шириной в самый длинный из исходов нарисованных строк (на десктопе плюс ячейка; нет
исходов — нет столбца). Раскладка зависит от ширины панели: берётся первая из трёх, где тексту остаётся не меньше
`MIN_LOG_TEXT_CELLS` (8) ячеек: 1) [время, who, текст, исход]; 2) без `who`: [время, текст, исход]; 3) [время, текст],
где исход стоит перед текстом (`✓ 0.3s Bash ls`), и обрезка текста с конца его не задевает. В последней раскладке текст
строки-ошибки красный. Раскладка одна на все строки секции (визуальная спецификация, §6.10).

**Подписи.** Там, где у раскладки нет столбца `who` (2 и 3), строка человека читается `you › …`, а строка движка (с
тегом, например `agent-message`) — `engine › …`: по одному тексту не видно, чья она. В раскладке [время, текст] исход
строки по-прежнему стоит первым, подпись идёт за ним. Остальные строки подписи не имеют. Без столбца `who` тип
субагента в журнале нигде не виден, кроме строки `spawned · тип: …`, если обрезка её не заденет: известное
ограничение, подписи для него нет (живая проверка 0.3.0, п. 11).

**Столбцы** выбираются по самому длинному исходу и самому длинному `who` среди нарисованных строк. Нарисованы те строки,
что помещаются (подробно — спецификация v2, §3); лишняя строка бывает, только если высоту блоков выше посчитали слишком
малой, и тогда хвост её обрезает. Длинный исход ниже по списку может отнять `who` у каждой строки. Это цена выровненных
столбцов: раскладка одна и для головы журнала, и для хвоста.

**Брошенный вызов** — исключение из строки `tool.call` выше. Вызов инструмента, который вернулся ошибкой, пока сам
вызов был брошен (человек прервал его или остановка), — пометка, а не сбой: `kind: 'info'`, строка не красная и
рисуется, как любая строка, не являющаяся ошибкой (текст обычный, `who` и исход приглушены), исход — одно время, без ✗,
как у остановленного субагента. Признак — `next.signal.aborted` после `await next(e)`. Он опирается на сигнал движка и
подтверждён вживую (живая проверка 0.3.0, п. 15 прошлого списка): у субагента, остановленного через `TaskStop`
(`Bash sleep 120`, `28.8s`), и у главного агента после Esc (`Bash sleep 30`, `4.6s`) строка без ✗ и не красная, а
`Bash false` остаётся красным.

**Ответ субагента** теряет разметку markdown, прежде чем попасть в строку `done`: парные `**` вокруг текста, обратные
апострофы и `#` заголовка в начале строки. Пара `**` снимается, только если к ней снаружи не примыкает буква ASCII,
цифра или `_`, поэтому `2**10 and 3**4` и `x**y` (показатели степени в коде) остаются. Буква другой письменности пару не
держит: в китайском, японском и тайском, где слова не отделены пробелами, и внутри слов кириллицы и хинди жирный
снимается так, как его читает markdown (`这是**重要**的` даёт `这是重要的`). `__` и одиночные или окружённые пробелами `**`
(`x ** 2`) тоже остаются. Это `plainText`, он идёт раньше `redact` и `shorten`.

**Символы форматирования.** Символы форматирования Unicode (категория Cf: управляющие символы двунаправленного
текста, невидимые пробелы, BOM) убираются из ветки, имени папки, строк списка Subagents (описание и тип), имён
MCP-серверов и каждого текста журнала, прежде чем секреты маскируются. Зачем: U+202E переставил бы то, что показывает
панель. Исключение — соединители ZWJ (U+200D) и ZWNJ (U+200C): они остаются только между двумя символами выше U+007F,
которые не пробелы. Так эмодзи-последовательности, склеенные ZWJ, остаются целыми, а персидская и индийские письменности
сохраняют свои соединители. Теги (U+E0020–U+E007F) тоже относятся к Cf и могут нести невидимый ASCII, поэтому они
убираются, кроме флагов Англии, Шотландии и Уэльса (чёрный флаг, теги `gbeng`, `gbsct` или `gbwls` и завершающий тег):
эти три остаются целыми. Любая другая последовательность тегов после чёрного флага убирается и оставляет простой чёрный
флаг. Рядом с символом ASCII, с пробелом любого вида или с краем текста соединитель ничего не соединяет, а спрятал бы
символ в названии ветки или разрезал бы секрет так, что маска его не находит: там он убирается.

`target` по инструменту:
- Bash — `command`;
- Read/Edit/Write/NotebookEdit — `file_path` относительно root;
- Grep/Glob — `pattern`;
- WebFetch — хост из `url`;
- Agent — `→ ${subagent_type}: ${description}`;
- `mcp__server__tool` — `server:tool`;
- остальные — пусто.

`redact` — набор регулярных выражений из `claude-flightdeck/hooks/core.ts` (MIT, с указанием авторства). Он маскирует bearer- и basic-токены, ключи `sk-`/`ghp_`/`xox*`, пары `token=`, `password=`, `*_KEY=`, флаги `--token` и пароли в URL.

## 5. Поведение панели

- **Окно:** id `session-panel`, заголовок `Session`.
- **Автооткрытие:** на `session.start` и на `session.attach`, но только если среди `$.session.surfaces()` есть `desktop`. В терминале панель открывается только командой.
- **Команда:** `/session-panel` только открывает панель и никогда её не закрывает: `UiPane.isShown` ранжирует лишь
  плагинные панели, поэтому одиночная панель считается показанной, даже когда её перекрывает встроенная вкладка
  десктопа, например Terminal (живая проверка 0.4.0), и команда не может отличить панель впереди от скрытой. Панель,
  которая открыта в любом состоянии (впереди, вкладкой за другой плагинной панелью или в ожидании размещения), команда
  открывает снова с `focus: true`, что выводит вкладку вперёд (это просьба, поверхность может её отклонить), и просит
  чтение проекта. Панель, которой нет в списке, открывается без `focus` и тоже просит чтение. Закрывает панель её
  собственный знак закрытия (в терминале ctrl+x x). Если панель не размещена, команда отвечает текстом с причиной из
  `UiOpenResult.reason`. Команда объявлена с `immediate: true` и срабатывает посреди хода.
- **Сворачивание:** состояние хранится в атоме `collapsed: Record<SectionId, boolean>`, где `SectionId` — один из
  `usage`, `turn`, `agents`, `mcp`, `sources`, `log`. Нажатие строится на карте из `$.store`, а не на карте своей
  сессии: оно оставляет то, что свернула другая сессия, и переключает одну секцию, на обратное тому, что панель
  показывает сейчас. Новая карта пишется в атом и в `$.store` под ключом `collapsed`. Если в `$.store` нет карты
  булевых значений (карты нет, её не удалось прочитать или это не карта), основой служит карта самой панели. На
  `session.start` карта читается из `$.store`. Значение из хранилища принимается, только если это объект с булевыми
  значениями. По умолчанию всё развёрнуто.
- **Файл хранилища** следует за идентичностью плагина. Десктопная установка пишет
  `session-panel_inline-fb64dc720a6f.json` (идентичность `session-panel@inline`), как видела живая проверка 0.3.0
  (п. 8); копия, загруженная под другой идентичностью (например, `session-panel@philarete-mods`), ведёт собственный
  файл, и состояние сворачивания у них не общее (живая проверка 0.2.0, п. 7). Сессии на 0.2.0 делят файл `inline` и
  пишут карту целиком, пока их не перезапустят.
- **Высота журнала:** журнал рисует столько строк, сколько помещается под блоками выше, но не меньше 8 (`MIN_LOG_ROWS`),
  из последних 200 событий, новые сверху; первые 8 видны всегда. События, которые не нарисованы, считает тусклая строка
  `+N more` внизу журнала, а заголовок показывает число всех событий (подробно — спецификация v2, §3). Если свернуть
  другую секцию, журнал получит её место. Если не помещаются и 8 строк, панель прокручивается (это делает движок). Где
  высота тела неизвестна (`bodyRows` равен 0), журнал рисует 15 строк (`MAX_LOG_ROWS`) естественной высоты, как в 0.2.0.
  Устройство и доказательства — в визуальной спецификации, §6.12.
- **`/clear` и `resume`** (`session.end` с причиной `clear` или `resume`) сбрасывают текущий и последний ход, субагентов, журнал и показания контекста (до следующего ответа выводится `—`); база стоимости задаётся заново; при `resume` на месте разговора оказывается другой.
- **Таймер:** `$.clock.every(30_000)`. Он делает `$.ui.invalidate('ui.render')` и обновляет статусы субагентов; каждый
  второй тик он обновляет MCP и, пока панель размещена и показана, просит чтение проекта (4.1, «Когда обновлять»).
  Открытие панели, командой или автоматически на `session.attach`, просит чтение проекта сразу.

## 6. Устройство

```text
claude_mods/                         маркетплейс
  .claude-plugin/marketplace.json    { name: "philarete-mods", plugins: [session-panel] }
  README.md, LICENSE (MIT), .gitignore
  plugins/session-panel/
    .claude-plugin/plugin.json       name, version, description, "types": "./types/index.d.ts"
    hooks/hooks.json                 { "modules": ["./register.tsx"] }
    hooks/register.tsx               события → атомы $.state (объявлены здесь: движок принимает источник
                                     состояния только из того же файла), команда, открытие, таймер
    hooks/view.tsx                   отрисовка Pane: блок Project, секции, шкалы, сворачивание
    hooks/stats.ts                   чистые функции: формулы 4.3, склейка интервалов,
                                     распределение стоимости 4.4, разбор вывода git 4.1,
                                     redact/shorten, форматы 3.2
    hooks/*.test.ts(x)               тесты (раздел 7)
    types/index.d.ts                 контракт PluginState['session-panel']
    LICENSE, THIRD_PARTY_NOTICES.md  лицензия мода и лицензии заимствованных проектов
```

- **Состояние** (`$.state`, атомы, переживают горячую перезагрузку): `usage`, `project`, `mcp`, `turn` (накопитель текущего хода), `lastTurn` (готовая статистика), `agents`, `log`, `collapsed`.
- **Отрисовка** только читает атомы и не делает вызовов `$`, кроме `$.ui.resolve`. Изменение атома перерисовывает панель.
- **`stats.ts`** не импортирует ничего от движка, поэтому тестируется изолированно.
- **Комментарии в коде** на английском, как и интерфейс.

## 7. Тесты и проверка

1. **`stats.ts`** через `claude plugin test`:
   - склейка интервалов (пересекающиеся, вложенные, раздельные);
   - формулы хода, включая `null`-случаи и потолок 5000 tok/s;
   - Cache %;
   - распределение прироста стоимости: монотонность (`max`), основной агент и субагенты;
   - все форматы;
   - `redact` и `shorten`;
   - разбор вывода git: статус (`--porcelain -z`) и числа строк (`--numstat`).
2. **Отрисовка** через `$.ui.mount` на `surface: 'desktop'` и `'terminal'`:
   - секции на месте;
   - блок Project: строки ветки и изменений, числа с минусом U+2212, пропуски (нет имени, ветки, изменений, строк);
   - нажатие на заголовок сворачивает секцию и пишет в `$.store`;
   - пустой `rateLimits` скрывает Usage.
3. `claude plugin validate plugins/session-panel` проходит без ошибок, `tsc` без ошибок.
4. **Ручная сверка в десктопе:**
   - Context % совпадает с индикатором контекста приложения;
   - лимиты совпадают со страницей usage;
   - после хода с субагентом Turn stats и Subagents заполнены правдоподобно.
5. **Чтения git:**
   - флаги git закреплены тестами на argv;
   - их действие проверено вручную на git 2.43: после изменения одних только stat-данных `.git/index` после чтения остаётся побайтно прежним, а при `diff.relative=true` числа строк по-прежнему покрывают весь репозиторий;
   - проверку повторять при обновлении git.
6. **Чего тесты не проверяют:**
   - настоящий git и настоящий `$.store` тесты не задействуют: аргументы и окружение git закреплены через моки;
   - заполнение журналом высоты и его прокрутку можно проверить только вживую: в тестовом наборе нет движка раскладки.

## 8. Риски и спайк

До основной реализации пишется каркас мода с пробами. Он копирует свои наблюдения в `<repo>/.spike/results.json` через
`$.fs.write`. Эта запись временная и удаляется вместе с каркасом. Пробы:

1. Размещается ли панель, открытая из `session.start` или `session.attach` на десктопе. Записать `isPlaced` и `reason`.
2. Набор полей `turn.step` (`turnId`, `agentId`, `model`) и последовательность видов чанков. Получаются ли правдоподобные TTFT и tok/s.
3. Входят ли субагенты в `cost.usd`: значение до и после шагов субагента внутри одного хода основного агента.
4. Отвечает ли `$.tool.call('WaitForMcpServers', …)` без запроса разрешения, сколько длится и какую форму имеет ответ.
5. Даёт ли `new Date().toTimeString()` локальное время.
6. Есть ли в usage чанка `stop` разбивка `cache_creation` по 5m/1h.

Если проба не подтвердится:

| Проба | Что делаем |
|---|---|
| 1 | панель открывается только командой |
| 2 | TTFT и Response убираются, Model time = Σ шагов без потока |
| 3 | формула Total из 4.1 |
| 4 | запасной источник MCP |
| 5 | время по UTC со смещением из `Intl` или без секунд |
| 6 | всё по ставке 5m |

Другие риски:
- **Windows.** Если движок ищет `git` сначала в рабочей папке, `git.exe` в корне репозитория запустился бы вместо git. Не проверено: разработка идёт на Linux; риск появился раньше задачи 10.
- **Большие репозитории с Git LFS.** Фильтр LFS запускается при чтениях. Частоту ограничивает задержка ×4.

Открытые живые проверки — проверки 8 и 10–13 визуальной спецификации (§11). Проверка 9, сигнал брошенного вызова,
закрыта живой проверкой 0.3.0 (4.7), а что она увидела по остальным, записано в §11. Проверка 2, черта над секцией
высотой в одну строку, закрыта спайком 0.4.0 (спецификация v2, §8.1): черта, заголовок секции и строка чипов заняли по
одной строке, а при `bodyRows` 65 уместились ровно 65 строк по 19 px. Первая из открытых (8) описана здесь, остальные
четыре (10–13) перечислены:
- **Терминал под новым корнем.** Корень панели получил `minHeight` (визуальная спецификация, §6.12), а как с ним и с
  хвостом журнала `height={0}` ведут себя Ink/Yoga, на живом терминале не видели. Проверить панель в доке (от 110
  столбцов) и встроенную. Если терминал не растит хвост, запасной ход — `rows: 0` на терминале, тогда он получит
  дерево 0.2.0.
- **Настоящая панель при трёх высотах** (10): спайки рисовали временное содержимое, а панель мода не видели. Пока
  содержимое помещается, журнал доходит до нижнего края и полосы прокрутки нет; сворачивание секции увеличивает журнал.
- **Первый кадр** (11): если на первой отрисовке `bodyRows` равен 0, журнал рисует 15 строк в одном Box до следующего
  `bodyRows`; смотреть, виден ли скачок.
- **Узкая панель, около 270 px** (12): раскладка не считает подпись (визуальная спецификация, §6.10), поэтому на краю
  раскладки строка движка может показать `engine › ` и ни одного знака текста; смотреть, сколько текста видно после
  подписи рядом с самым длинным исходом.
- **Панель фоновой сессии** (13): `isShown` движка называет лишь ту из плагинных панелей сессии, что впереди, и панель
  Session, когда она одна, показана всегда (4.1). Если открыты две сессии десктопа, перечисляет ли `$.ui.panes()`
  фоновой сессии панель как размещённую и показанную? И когда в сессии впереди встроенная вкладка десктопа (Diff,
  Terminal)? Если да, минутное чтение этой сессии идёт, как в 0.3.0, и находка 2 живой проверки 0.3.0 не закрыта. Ответ
  живой проверки 0.4.0 на второй вопрос: да, при вкладке Terminal впереди одиночная панель Session размещена и показана
  (команда 0.4.0 её закрыла), и минутное чтение идёт; пользователь решил оставить его как есть (2026-10-13). Две сессии
  десктопа не проверялись.

## 9. Разработка и установка

- **Исходники:** `<repo>`, git. Коммиты только с разрешения пользователя.
- **Горячая перезагрузка:** `rsync -a --delete --exclude .claude-plugin/types/ plugins/session-panel/ ~/.claude/dev-mods/<session-id>/session-panel/` после каждой правки. Движок перезагружает мод в конце хода. Папку `.claude-plugin/types/` движок пишет сам, она в `.gitignore`.
- **Установка:** `claude plugin marketplace add philarete173/claude_mods` (или путь к локальному клону) и
  `claude plugin install session-panel@philarete-mods`. После установки копия в dev-mods удаляется, чтобы мод не
  загрузился дважды.
- **Обновление установленной копии:** 1) выпуск: поднять `version` только в
  `plugins/session-panel/.claude-plugin/plugin.json` (с 0.3.2 запись плагина в `.claude-plugin/marketplace.json` версии
  не несёт) и выполнить команду `claude plugin tag plugins/session-panel`, которая создаёт тег
  `session-panel--vX.Y.Z`; 2) выполнить `claude plugin marketplace update philarete-mods`, затем
  `claude plugin update session-panel@philarete-mods`; 3) начать новую сессию. Движок загружает снимок из
  `~/.claude/plugins/cache/philarete-mods/session-panel/<version>/`, поэтому правка в репозитории доходит до
  установленного мода только после обновления.
