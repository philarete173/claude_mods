## Что починить

1. **Продолжение субагента через SendMessage пишется как новый запуск, и его цена обнуляется** (средняя, видно вживую). С движка 2.1.308 SendMessage, будящий субагента, поднимает `agent.spawn` с `e.resume.agentId` (`AgentSpawnInput.resume` в типах 2.1.308; в 2.1.288 поля нет), а мод его не читает. Хук `agent.spawn` (`register.tsx:1056-1074`) строит строку заново (`startedAt` — сейчас, `costUsd: null`, без `restored`), затирает прежнюю по id (`:1072`) и пишет `spawned · …` (`:1073`); `reviveAgent` (`:926`) видит `running` и выходит (`:655`), так что строки `resumed` нет. Вживую после переоткрытия: SendMessage восстановленному «Repro check of a you line» дал `spawned · general-purpose: Repro check of a you line` и `done · $0.005 — OK`, в Subagents `$0.005` без `+` (оба `+` смотрят только на `row.restored`). Без переоткрытия то же: у продолженного живого субагента цена сбрасывается до расхода после пробуждения, прежняя уходит в Session. Проверка 39 не проходит. Предложение: при `e.resume !== undefined` (или известном id) оставлять строку — `running`, `endedAt: null`, сохранить `restored` и `costUsd` — и писать `resumed · …`.
2. **Отчёты субагентов пропадают из восстановленного лога; проверка 43 ждёт `peer` по неверной предпосылке** (низкая-средняя, видно вживую). Вживую отчёт субагента открывает ход текстом с тегом `agent-message` и пишется `engine` / `agent-message` (`register.tsx:900-903`). Восстановление оставляет из строк движка только `peer` и `task-notification` (`restore.ts:146`), поэтому после переоткрытия отчётов в логе нет: ни один из четырёх сегодняшних не вернулся. Фраза `Another Claude session sent a message:`, которую ждёт правило `peer`, в 2.1.321 — подпись интерфейса для удержанного сообщения другой сессии, а не текст отчёта; на ней построены тесты (`stats.test.ts:1971`, `restore.test.ts:187`, `register.test.ts:3409`), `README.md:119-121`, `:214` и проверка 43. Предложение: восстановление оставляет все теги движка, как живой путь; README и проверку 43 исправить на `agent-message`. Заодно отчёт (`<agent-message from=…>`) мог бы закрывать восстановленного субагента: сейчас оба ревьюера, отчитавшиеся между ходами, после переоткрытия — `○ ended` (п. 3).
3. **После переоткрытия субагенты и задачи, чьё уведомление пришло посреди хода, — `○ ended`** (низкая, видно вживую, описано в `README.md:213-227`). Движок не хранит такие уведомления строками, поэтому оба ревьюера, закончившие и отчитавшиеся, и упавшая `sleep 1; exit 1` (не красный ✗) после переоткрытия — `○ ended`; в этой сессии так 3 из 6 субагентов и 3 из 6 восстановленных задач. Отчёт субагента между ходами — строка, и по нему можно закрывать субагента (п. 2).
4. **Восстановленная строка `done` показывает служебный текст движка вместо ответа** (низкая, видно вживую). Агент «Check 36» закончил без отчёта; вживую его строка — `done · $0.007 — OK` (ответ агента), после переоткрытия — `done — The subagent ended without delivering a report through Suba…` (текст `<result>` из уведомления).
5. **Без `session.start` нет ни восстановления, ни таймера, и это не видно** (низкая, по ревью). Восстановление, команда `/session-panel`, 30-секундный таймер и автооткрытие панели висят на `session.start` (`register.tsx:721-734`). У пользователя первым работает плагин «cc-plugin-sec-default», который пропускает события мимо чужих хуков (в 2.1.321 — `next.to(e, tier)` управляемого плагина); в этой проверке он пропустил хуки lot-map и ponytail, но не `session.start` мода — восстановление прошло после обоих переоткрытий. Если пропустит, панель останется пустой без признака. Предложение: восстанавливать и на первом `turn.start` основного цикла, если `session.start` не было, а атомы пусты.
6. **Маска** (низкая):
   - числа и литералы после закавыченного ключа теперь видны (0.5.2, описано в `README.md:182-192`, `NOT_PLAIN` `stats.ts:431`): `curl -d '{"username":"admin","password":123456}'`, `"DB_PASSWORD": 12345678`, `'password' => 123456`, `{"token": 482913}`, `{"client_secret": 0e47}`; 0.5.1 их скрывал. Предложение ревью безопасности: оставлять числа открытыми только после имён счётчиков (`max_token` и подобных), а после `password`, `pwd`, `secret`, `api_key` и `*_key` скрывать;
   - по-прежнему съедаются `";` и `'` после значения (`stats.ts:218`, `:529-532`, описано в `README.md:195-197`): вживую `Bearer ••• echo ok`, `'secret_key=•••`, `'aws configure set aws_secret_access_key •••`;
   - по-прежнему лишняя маска у строк и прозы (описано в `README.md:194-201`): `{"pwd": "/srv/app"}`, `grep … src/`, `Authorization: required…`, `TorchBearer •••`, `1️⃣2️⃣` → `12`;
   - только на подобранном вводе — 240 минимальных регрессий в четырёх группах: `UNQUOTED_KEY` (`stats.ts:499-512`) берёт приклеенный следующий якорь за своё значение (`secretkey=atoken= VAL` → `secretkey=••• VAL`; в `access_key=Bearer`, перевод строки, `TOK;` токен виден); `NO_ANCHOR` (`:440-445`) показывает префикс перед внутренним именем (`"secret": VAL-secret:x`); значения с `?=` и `+=` уходят в SECRETS, который читает только `[=:]` (`:222`), и видны целиком (`"password": pwd+=VAL`), хотя `README.md:185-186` обещает обратное; новые имена `*_key` в AUTH_SCHEME (`:531`) оставляют `Authorization: c VALprivatekey:` открытым. Старые подобранные случаи (`ESC(ghp_`, `\x9b Bearer`, `--token` после 8-битного CSI, невидимый символ, склеивающий токен со словом) остались.
7. **Восстановление верит тексту уведомления** (низкая, по ревью безопасности). Восстановление узнаёт уведомление по тексту (`restore.ts:146-151`), живой путь — по `origin.kind` (`register.tsx:1107`). Набранный, вставленный или пересланный через SDK `<task-notification>` закрывает восстановленную задачу с выдуманными статусом и временем или живого субагента с выдуманным `done — <result>` (маскируется). Промпт, начинающийся с фразы сводки, стирает всё восстановленное до него (`restore.ts:138-142`). `README.md:227-228` описывает подделку плагином и фразу сводки, но не набранное уведомление.
8. **У восстановления нет предела по времени** (низкая, по ревью безопасности). Тип и описание каждого запуска и тексты каждой фоновой задачи чистятся сразу (`restore.ts:92-93`, `:122`), лениво — только 200 строк лога. Подобранные тексты `a.a.…` по 4 КБ — около 5.3 мс каждый: 1000 запусков — 10.6 с, 1000 фоновых Bash — 12.1 с, синхронно, одним обратным вызовом. Мод не ограничивает строки (`register.tsx:285`); «4096 строк» в `README.md:211` — предел движка, а в одной строке может быть много вызовов (20 480 обычных запусков — 1.5 с). Обычная нагрузка быстрая. Не проверено, замораживает ли долгое восстановление движок или интерфейс.
9. **Мелочи** (низкая):
   - промпт, начинающийся с `[Image: source: `, и промпт между двумя служебными блоками не получают строку `you` ни в ходе (`register.tsx:900`), ни посреди хода (`:1099`) (по ревью; вживую сообщения со скриншотами, где текст впереди, писались как `you`);
